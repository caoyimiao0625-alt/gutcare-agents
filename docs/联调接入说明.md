# 联调接入说明（业务后端 → 智能体服务）

> 面向 APP 与业务后端开发方。目标：让双方在**不读智能体源码**的前提下完成接入、
> 异常演练和验收。完整接口定义见 `docs/openapi.yaml`；需要通用请求/响应结构样例时，先单独提供 `testdata_v4` 并设置 `GCA_FIXTURE_ROOT`，再运行 `python tools/make_samples.py`，输出在 Git 忽略的 `data/generated_samples/`。默认 mock 样例不代表真实识别效果；F08 最小联调不依赖该测试包。

## 1. 启动服务

```powershell
cd gutcare-agents
$env:GCA_FIXTURE_ROOT="<本机测试包目录>"   # 仅演示模式需要（/v1/demo/*）
$env:GCA_INTERNAL_TOKEN="与后端约定的内部令牌"
$env:GCA_MODE="mock"        # 联调期建议先用 mock：不联网、不消耗额度、响应结构完全一致
python -m gutcare_agents serve --port 8100
```

- `mock`：结构联调。识图类结果会返回 `insufficient_data` 并说明“未执行真实识别”，**不会**伪造结论。
- `live`：真实模型。需要 `GCA_API_KEY`，会把响应录制到 `replays/`。
- `replay`：读录制结果。断网可演示、结果可复现，适合评审与回归。
- 生产/联调建议加 `GCA_INTERNAL_TOKEN`；`/healthz` 与演示控制台不受鉴权限制。

健康检查：`GET /healthz` → `{"ok":true,"mode":"mock"}`；能力清单：`GET /v1/meta`。

## 2. 任务类型与入口

| 任务类型 | 智能体 | 接口 | 说明 |
|---|---|---|---|
| `report_extract` | Medical | `POST /v1/tasks` | 图片/PDF 报告字段抽取；PDF 优先读取内嵌文本，扫描页转图像；返回候选值 + 原文依据 + 待确认字段 |
| `report_text_extract` | Medical | `POST /v1/tasks` | **视觉降级路径**：从 OCR/转写文本抽取（传 `options.text` 与 `options.source_id`），契约与报告抽取一致 |
| `report_ocr` | Medical | `POST /v1/tasks` | 可见文字转写，遮挡写 `[遮挡]` |
| `advice_doc_extract` | Medical | `POST /v1/tasks` | 模拟医嘱文书抽取，保留“仅测试”标记 |
| `meal_recognize` | Diet | `POST /v1/tasks` | 单餐识菜，返回候选食物与不确定项 |
| `stool_record` | Stool | `POST /v1/tasks` | 排便记录结构化校验，不调用模型 |
| `stool_image_recognize` | Stool | `POST /v1/tasks` | 单张图片质量评估和 Bristol 1—7 型候选；患者需确认，不从图像判断便血或疾病 |
| `trend_analyze` | Trend | `POST /v1/tasks` | 指定时间窗的趋势与时间关联 |
| `advice_generate` | Advice | `POST /v1/tasks` | 基于已有观察生成建议（一般由综合分析内部调用） |
| `analysis` | Orchestrator | `POST /v1/analysis` → `GET /v1/tasks/{id}` | 综合分析，异步，含阶段时间线 |
| `assistant_chat` | Conversation | `POST /v1/assistant/chat` | 解释已有结果；药物/诊断类问题不调用模型 |
| — | 规则引擎 | `POST /v1/safety/check` | 即时危险征象，**不调用模型**，同步返回 |

## 3. 请求字段（最小可用）

```json
{
  "task_id": "后端任务号，建议直接复用",
  "kind": "report_extract",
  "patient_id": "内部受控标识",
  "time_range": {"start": "2026-09-01T00:00:00+08:00", "end": "2026-09-08T00:00:00+08:00"},
  "records": [
    {"record_id": "...", "patient_id": "...", "kind": "stool",
     "occurred_at": "...", "created_at": "...", "status": "confirmed", "version": 1,
     "data": {"bristol_type": 4, "blood_reported": false}}
  ],
  "profile": {"patient_id": "...", "diagnosis_status": "confirmed", "diagnosis": "IBS", "profile_version": 3},
  "files": [{"file_id": "doc_123", "path": "受控路径或预签名 URL", "mime": "image/png", "kind": "report"}],
  "options": {"force_refresh": false}
}
```

PDF 报告沿用 `kind=report_extract`，文件填写 `mime=application/pdf`、`kind=report`；
排便图片使用 `kind=stool_image_recognize`，文件填写 `kind=stool_image`、`mime=image/jpeg` 或 `image/png`。
PDF 最多处理前 5 页；若截断，结果会携带 `pdf_processing.truncated=true` 和不确定性提示。

三条必须遵守的口径（来自测试包 `docs/字段与验收.md`，与业务后端一致）：

1. `status` 只有 `confirmed` 参与分析；`pending_confirmation / deleted / superseded` 会被排除。
   智能体不会把“缺失”解释成“没发生”。
2. `occurred_at` 是发生时间、`created_at` 是录入时间，补录按前者归档。
3. 所有记录的 `patient_id` 必须与请求一致；不一致直接返回 `patient_scope_violation`。

**接入参考实现**：仓库自带一条“只读 SQLite → TaskRequest”的适配路径
（`Fixtures.analysis_request_from_db`，用测试包 `fixture.sqlite` 验证过：与 seed 数据算出的
统计结果完全一致，且写入会被数据库拒绝）。正式联调时把这条路径替换成
“调用后端授权接口 / 读取只读副本”即可，Agent 与编排逻辑无需改动。

## 4. 响应要点

```json
{
  "task_id": "...", "agent": "medical", "status": "ok",
  "agent_version": "0.2.0", "prompt_version": "medical-v1", "model_id": "deepseek-chat",
  "input_record_ids": ["..."], "input_versions": {"...": "2"}, "input_snapshot_hash": "...",
  "observations": [
    {"obs_id": "medical_obs_001", "kind": "fact", "statement": "原文结论：...",
     "source_record_ids": ["doc_123"],
     "source_refs": [{"ref_type": "report_page", "ref_id": "doc_123", "locator": "p1"}],
     "confidence": "high"}
  ],
  "uncertainties": [{"code": "redacted_regions", "message": "有 2 处遮挡，相关字段已留空"}],
  "needs_confirmation": true,
  "confirmation_fields": ["report.diagnosis", "report.suggestions"],
  "findings": [{"code": "unsafe_content_blocked", "severity": "error", "action": "dropped", "message": "..."}],
  "data": {"...": "Agent 专属结构化结果"}
}
```

**状态语义**（业务后端需要据此映射自己的任务状态）：

| 智能体状态 | 含义 | 后端建议动作 |
|---|---|---|
| `ok` | 完整成功 | 保存结果，进入待确认/已完成 |
| `partial` | 部分成功（某些图像未识别、模型叙述缺失、校验删了条目） | 保存结果 + 展示 `uncertainties`/`findings` |
| `insufficient_data` | 输入不足以支撑该结论 | 展示原因，引导补充记录；**不要**标成失败 |
| `failed` | 执行失败（超时/不可用/输出结构错误） | 保存失败原因，允许重试；原始数据不动 |
| `skipped` | 该阶段按输入条件跳过 | 无需处理 |

`findings` 是输出校验记录：`action=dropped` 表示这条内容因无依据/违规被删除。
前端应能展示“为什么少了一条建议”，这是可解释性的一部分。

## 5. 幂等、重试与超时

- **幂等**：同一 `patient_id` + 同一 `kind` + 同一输入快照（记录 id/version/status 集合）会直接复用已有任务，返回体里带 `report.reuse.reused_task_id`。传 `options.force_refresh=true` 强制重跑。
- **重复点击**：后端按 `idempotency_key` 去重即可；智能体侧也会挡住同快照重复分析。
- **超时建议**：单个 Agent ≤ 60s（`GCA_TIMEOUT_S`）；综合分析整体建议后端超时 200s。
- **重试策略**：只对 `model_timeout / model_unavailable / agent_timeout / model_rate_limited` 重试，
  指数退避 1—2 次；`model_invalid_output` 只在智能体内部做一次“带校验反馈”的修复重试。
- **部分失败**：`analysis` 返回的 `stages[]` 会标明哪个阶段失败；`report.degraded[]` 给出人话说明。
  领域 Agent 失败不会阻断整体流程，也不会用空白数据伪装完整结论。

## 5.1 取消

`POST /v1/tasks/{task_id}/cancel` → `202`，返回 `{"cancelled": true/false, "status": "..."}`。

- **协作式取消**：只在阶段之间检查，正在跑的模型调用不会被强杀（避免半截结果写库）；
- 已完成的阶段结果保留（`report.cancelled.completed_stages`），用户可重新发起分析并复用；
- 已结束的任务不会被“取消”覆盖（返回 `cancelled=false` 与原状态）；
- APP 侧建议：取消后停留在任务详情页，展示“已取消 + 可重新发起”，不要清空已有记录。

## 6. 错误码

| code | HTTP | 含义 | 处理建议 |
|---|---|---|---|
| `invalid_request` | 400 | 缺字段/JSON 非法 | 修请求，不要重试 |
| `patient_scope_violation` | 400 | 记录与患者不匹配 | 说明越权，审计记录，不要重试 |
| `unauthorized` | 401 | 内部令牌错误 | 修配置 |
| `file_not_found` / `unsupported_media_type` | 400 | 文件缺失/格式不支持 | 提示用户重新上传 |
| `image_low_quality` | 400 | 图像不可用 | 允许手动输入，不阻断记录 |
| `input_data_insufficient` | 400 | 输入不足以完成任务 | 引导补充 |
| `model_unavailable` / `model_timeout` / `model_rate_limited` | 400 | 模型侧故障 | 可重试；记录与安全规则不受影响 |
| `model_invalid_output` | 400 | 输出结构不合规 | 智能体内已重试；仍失败则降级 |
| `agent_timeout` | 400 | 阶段超时 | 可重试 |
| `internal_error` | 500 | 未预期异常 | 报障，附 `request_id` |

## 7. 异常演练（现场可复现）

`POST /v1/analysis` 支持在 `options` 里注入故障，用于演示“模型故障时系统仍可用”：

```json
{"options": {"simulate_faults": ["advice"], "simulate_delay_ms": 800}}
```

`simulate_faults` 可填 `medical / diet / stool / trend / advice / all`。注入过故障的任务
不进入幂等复用（避免污染后续正常分析）。

CLI 等价写法：`python -m gutcare_agents analyze --patient SYN002 --fault advice`。

## 8. 联调验收清单

> 一条命令先跑自检：`python tools/smoke_test.py --base-url http://127.0.0.1:8100 [--token xxx]`
> 它会逐项输出 PASS/FAIL/SKIP（健康、能力清单、规则不误报、L3 触发、越权拒绝、综合分析与降级），
> 退出码 0 表示可进入下面的手工验收。

1. `GET /healthz`、`GET /v1/meta` 可访问，`mode` 与预期一致；
2. 单个报告抽取：返回候选字段、证据定位、`needs_confirmation=true`；
3. 单餐识别：模糊图返回 `insufficient_data` + 可手动保存的降级路径；
4. 综合分析：`stages` 有序、`report.advice` 每条都有依据编号；
5. 无已确认诊断（如 SYN009）：`report.advice` 为空且给出原因；
6. 注入 `advice` 故障：任务 `partial`，记录与风险提示仍在；
7. 提交黑色柏油样便：`/v1/safety/check` 在 50ms 内返回 L3 提示，且同事件 1 小时内不重复轰炸；
8. 同一请求重复提交：返回同一 `task_id`（幂等），不产生重复报告。

## 9. 并行开发建议

- 后端先用 `mock` 模式对接，接口结构、状态枚举、错误码完全一致；
- 智能体侧改动 `prompt_version` / `model_id` 时会在响应里体现，后端可据此做灰度对照；
- 样例响应更新通过 `python tools/make_samples.py` 重新生成，避免手写文档漂移。
