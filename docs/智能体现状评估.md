## 1. 现在这些智能体到底做到了什么

### 1.1 三种入口，能力不同

| 入口 | 谁调用 | 跑什么 | 当前状态 |
|---|---|---|---|
| `POST /internal/v1/tasks`（F08） | 业务后端 Worker | 只跑 Trend + Advice + 校验；领域阶段按输入条件触发 | 已实现，本地模拟后端通过 |
| `POST /v1/tasks`（单任务） | 内部/联调 | Medical（图片/PDF/文本）、Diet、Stool（记录/图片）、Trend、Advice、Conversation | 已实现 |
| `POST /v1/analysis`（同步综合分析） | 演示控制台/CLI | intake → domain → trend → advice → validate | 已实现 |

**重要事实**：F08 链的冻结输入只包含**结构化记录**，不含报告图片、食物图片——所以当前 F08 实际只用到 Trend/Advice/Stool(记录校验)。这也解释了为什么 `docs/智能体详细开发文档.md` 把 Medical/Diet 标为“未在当前 F08 链运行”。

### 1.2 七个角色逐个看

| 角色 | 能做的事 | 不能做的事（代码层面就限制住） |
|---|---|---|
| Orchestrator | 阶段编排、依赖、超时、重试、幂等、领域结果复用、部分成功汇总、取消 | 不做医学判断；不扩大数据访问范围 |
| Medical | 报告**图片**字段抽取；**PDF**（先取文本层，扫描页渲染成图）；**纯文本**抽取；医嘱文书抽取；可见文字转写 | 不补造被遮挡的数值/单位；不把“疑似”写成“确诊”；不推断剂量 |
| Diet | 食物图识菜（候选 + 画面依据 + 不确定项）；无图时接受文字描述 | 不给热量/营养素；不判断“是否健康” |
| Stool | 记录合法性校验（Bristol 1—7、缺失、无效值）；**新增**图片质量评估 + Bristol 候选 | 不从图片判断便血/炎症/肿瘤；候选必须患者确认；候选值写不进已确认记录 |
| Trend | 确定性统计（计数、缺失日、Bristol 分布、服药打卡、餐次→症状 6h 邻近、心情序列）+ 模型叙述 | 模型不能改数字；不得写因果；“没有记录”≠“没有发生” |
| Advice | 检索知识库 + 引用观察，生成带 `obs/KB` 证据的建议；数据不足降级 | 每条的引用解析不到就删除；禁止剂量/诊断/因果/绝对化 |
| Conversation | 解释已有结果、整理随访问题；药物/诊断类问题**不调模型**直接安全回应 | 不改业务数据；不越权取数 |
| Validator（非大模型） | 结构 → 证据可解析 → 禁用表述 → 数值落地；日期不误判 | 只做删/降级，不“提醒模型注意” |

### 1.3 这次改动新增的三块（都读到了代码）

1. **F08 适配层**（`f08_adapter.py`，363 行）
   - 严格校验派发（`schema_version=1.0`、`analysis_type` 枚举、幂等键、任务 ID 复用冲突 409）；
   - 读冻结输入时逐条校验 `record_type/record_version/locator/confirmation_status`；
   - **心情记录单独通道**：四项授权同时为真才接收，载荷只允许 `occurred_at/mood_level/emotion_tags`，绝不收自由文本；标签白名单与去重；
   - **医学冲突**（`medical_fact_conflict`）若被标成 confirmed 直接拒绝；未解决的冲突不进入分析；
   - 证据键 `(source_type, source_id, source_version, locator)` 与快照严格对齐，**快照外的引用整条观察不回调**；
   - 回调字段裁剪（observations ≤30、evidence ≤100、长度上限），`callback_id` 由任务+快照稳定生成，重复回调幂等；
   - **本地日记（F08Journal）**：先落派发收据再回 202；回调内容发送前落盘；重启扫描未完成任务（有回调重发、无回调重新分析）；暂时性错误各重试 3 次；404/409 视为终态停止，不伪造失败；`CALLBACK_ID_CONFLICT` 显式报错。
2. **PDF 双路径**（`pdf_input.py`）：`pypdf` 取文本层（≤5 页、≤12MB、加密/损坏明确报错）；扫描页用 Poppler `pdftoppm` 渲染后走视觉。
3. **排便图片候选**（`agents/stool.py` 的 `_run_image` + `prompts/stool.image.v1.md`）：先质量门槛，再给 Bristol 候选，`appearance/evidence` 过一层禁用词与“便血/黑便/炎症/肿瘤/诊断”正则过滤，命中即清空并留 `finding`。

另外两处工程性改进值得记一笔：

- **快照指纹更严**：`Orchestrator.run` 的幂等快照值现在把 `mode/文本模型/视觉模型/提示词目录指纹/知识目录指纹/规则文件哈希` 都算进去——改提示词或规则会自然失效，不会拿旧结果冒充新分析；
- **领域缓存按患者隔离**：缓存键加入 `request.snapshot_hash()`（含患者与记录版本），命中后还二次校验 `patient_id` 与输入快照，避免跨患者复用识别候选。

## 2. 与后端契约的覆盖度（关键缺口）

对照 `contracts/agent/agent-v1.yaml`（本次已读）：

| 后端契约端点 | 智能体侧 | 说明 |
|---|---|---|
| `POST /internal/v1/tasks`（派发） | ✅ 已实现（`api.py`） | 未配置双方令牌时返回 503；要求 `Idempotency-Key` |
| `GET /agent/analysis-tasks/{id}/inputs`（F08 冻结快照） | ✅ 已实现 | 校验任务 ID、类型、版本、快照哈希、授权、来源字段 |
| `POST /agent/analysis-tasks/{id}/result` | ✅ 已实现 | 状态映射 `succeeded/partial/needs_input` |
| `POST /agent/analysis-tasks/{id}/fail` | ✅ 已实现 | 固定 `AGENT_ANALYSIS_FAILED` |
| `POST /agent/analysis-tasks/claim` | ⚠️ 仅本地工具用 | `tools/f08_claim_once.py`，正式环境由后端 Worker 领取 |
| `POST /agent/tasks/{id}/runs`（逐 Agent 运行元数据） | ❌ 未接入 | 当前只上报最终 result/fail，链路审计粒度较粗 |
| `POST /agent/medical-parse-requests/{id}/candidates`（单文档字段候选） | ❌ 未接入 | 后端已有“医疗文档解析请求”契约，智能体侧只有独立的 `/v1/tasks` 入口，未接这条链 |
| `GET /agent/medical-parse-requests/{id}/inputs` | ❌ 未接入 | 同上 |
| `POST /agent/record-image-recognition/...`（饮食/排便图片识别请求） | ❌ 未接入 | 智能体有识图能力与提示词，但没有接后端的“请求-候选”协议（含一次性图片能力 URL） |
| `POST /agent/advice/{task_id}/callback`（F09 独立建议） | ❌ 未接入 | 当前建议是 F08 结果的一部分，尚未接 F09；`ADVICE_NOT_APPLICABLE` 的“不得重试”语义也还没有对应实现 |

**判断**：F08 这条主链是通的；但后端已经把医疗解析、记录图片识别、独立建议都定义成契约，智能体侧目前是“有能力、没接线”。这不是缺陷，而是明确的下一阶段工作——答辩时应当这样表述，别说成“已完成”。

## 6. 答辩口径（能说 / 不能说）

**能说**

- 参考多智能体协作、检索增强生成、可归因生成的研究，**自行实现**了阶段编排、确定性统计、本地检索与冻结证据校验；
- F08 冻结快照链路（派发→读快照→分析→回调）在本地以契约级模拟服务验证通过，含 12 类故障与恢复场景；
- 状态映射与证据边界是**代码强制**的：快照外引用整条丢弃、冲突记录不转事实、心情记录四授权才收；
- 无模型时安全规则与记录校验仍可用。

**不能说**

- 不声称复现了 AutoGen / 原版 RAG / FActScore / 医疗 RAG 基准；
- 不把本地协议测试当临床有效性或真实后端集成证明；
- 不给“图片识别准确率 9x%”这类数字（没有标注集，未测）；
- 不说“已接入医疗文档解析/图片识别/F09 建议”的后端流程（未接）。
