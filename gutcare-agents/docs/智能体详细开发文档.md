# GutCare 智能体详细开发文档

更新时间：2026-10-20（交付包副本）。本文以 `gutcare-agents` 当前代码和业务后端 `gutcare-agent` 的 F08/F09 契约为准，区分已实现、已本地验证和仍需真实环境验证的部分。后端源码核对固定在提交 `ac45fa0d53e73b699ab11fce0bcabf74a122f05a`，后续后端更新需重新运行兼容检查。

## 1. 目标与边界

系统为肠道健康记录提供报告抽取、食物识别、排便图片候选分类、跨记录趋势、建议和对话解释。业务后端负责身份、患者归属、授权、记录确认、任务状态及患者查询；智能体只读取业务后端提供的冻结输入，执行推理并回调结构化结果，不直接读写业务数据库。F08 是综合健康分析/周期小结的任务流程。

当前优先目标是**跑通真实协议链**，分析准确性和真实模型验收放在下一阶段。`mock` 只用于契约和流程联调，不能作为图片识别或临床准确性证明。

## 3. 现有内部数据结构

`TaskRequest` 是智能体编排层的输入：`task_id`、`patient_id`、`kind`、时间窗、已确认记录、文件及选项。`AgentResult` 是单个智能体输出：状态、观察、来源记录 ID、来源引用、疑点、待确认字段、模型/提示词版本和校验发现。`TaskRun` 汇集阶段状态和患者可读报告。原有 `/v1/analysis` 使用此结构；F08 通过专门适配层转换，避免将业务后端契约混入各领域智能体。

数据筛选原则：只将 `confirmation_status=confirmed` 的记录纳入统计；未解决的 `medical_fact_conflict` 绝不转成确定医学事实；缺失记录不能解释为症状没有发生。图片候选仍须患者确认，不能写回已确认记录。

## 4. F08 接入协议与实现

契约来源：[后端 Agent OpenAPI](https://github.com/yeyeyelzy/gutcare-agent/blob/main/contracts/agent/agent-v1.yaml)、[后端集成 ADR](https://github.com/yeyeyelzy/gutcare-agent/blob/main/docs/ADR/0005-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E8%BF%87%E5%86%85%E9%83%A8API%E9%9B%86%E6%88%90.md)、[F08 冻结任务 ADR](https://github.com/yeyeyelzy/gutcare-agent/blob/main/docs/ADR/0012-f08-frozen-analysis-task-workflow.md)，以及[后端实际 API](https://github.com/yeyeyelzy/gutcare-agent/blob/main/backend/src/gutcare/analysis/api.py)。后端 Worker 应独占领取任务，并向智能体 `POST /internal/v1/tasks` 派发 `{task_id, analysis_type, schema_version:"1.0"}`，带服务 Bearer 和 `Idempotency-Key`。智能体返回 202 `{task_id,accepted:true}`。本仓库 `gutcare_agents/api.py` 已实现该入口。没有配置双方服务令牌时拒绝 F08 派发。

智能体收到派发后：

1. 从 `GET /internal/v1/agent/analysis-tasks/{task_id}/inputs` 读取**冻结快照**，校验任务 ID、分析类型、版本、快照哈希、授权范围和记录来源字段。
2. `gutcare_agents/f08_adapter.py` 将后端记录类型映射到现有 `TaskRequest` 的 `diet/stool/symptom/mood/medication` 等种类；保留源类型、UUID、版本、locator 作为证据索引。`medical_fact_conflict` 被排除。心情仅在四项授权同时有效时接收，载荷严格限定为 `occurred_at/mood_level/emotion_tags`，不会接收自由文本备注。
3. `Orchestrator` 运行分析。F08 每条业务任务强制按自身任务 ID 运行，避免旧任务的同快照缓存结果替代新任务。
4. 将内部 `succeeded/partial/insufficient_data` 映射为后端 `succeeded/partial/needs_input`。无法分析时走 `/fail`，错误码为 `AGENT_ANALYSIS_FAILED`。回调 ID 由任务与快照稳定生成，重复回调可幂等识别。
5. 只传送可对应冻结快照的观察和证据。证据严格使用后端冻结的 `source_type/source_id/source_version/locator`，不从模型输出臆造来源。回调字段严格为 `callback_id,status,schema_version,summary,observations,evidence,uncertainties,missing_data`，并限制长度/数量。
6. 业务后端按其自身规则校验证据并落库；患者通过 `GET /api/v1/analysis-tasks/{task_id}` 查询，必须使用患者身份令牌。

本地开发辅助脚本 `tools/f08_claim_once.py` 可以代行缺席的 Worker，领取**一条**任务并派发给已启动的 Agent 服务。这是联调工具，正式部署仍由业务后端 Worker 负责领取与重试。

### F08 异常处理与重启恢复（已实现，2026-10-18）

`gutcare_agents/f08_adapter.py` 的 `F08Journal` 在 Agent 本地 SQLite 保存派发收据和待发回调，不保存后端冻结输入原文。Agent 收到派发后先持久记录，再返回 202；同一 `task_id`、同一分析类型的重复派发不会启动第二份并行分析，不同分析类型返回冲突。结果/失败回调内容在发送前持久化，服务重启会扫描未完成任务：已有回调则原样重发，不重新分析；尚无回调则重新读取冻结输入，后端授权和任务状态会再次校验。

冻结输入读取和回调发送遇到暂时性网络错误或服务端 5xx 时各最多尝试 3 次，间隔递增。回调应答丢失时，即使后端可能已经落库，也只重发相同 `callback_id` 和内容，**不补发失败回调**。重试耗尽后保留待发记录，等待后端再次派发或 Agent 服务重启恢复。分析代码本身失败时才准备 `/fail` 回调，并同样先落本地日志。后端输入返回 404/409，或回调返回表示任务终态的 404/409 时，停止本地任务，不用失败回调覆盖后端终态；`CALLBACK_ID_CONFLICT` 会被明确记为冲突并抛出，避免伪装为正常取消。其他 4xx 拒绝会停止并保留诊断状态，避免无休止重发。

本地恢复仅保证**单实例**运行与同一 SQLite 文件上的重启幂等；多实例同时消费、跨机共享存储和后端 Worker 租约续期尚未实现。后端目前领取时设置 5 分钟租约；项目当前预计单次分析在 5 分钟内完成，因此本阶段不做续租。该时限尚未在真实模型的大样本运行中验收；若出现超时，需与后端约定续租或调整任务执行策略。

### 状态映射

| 内部结果 | F08 回调 | 说明 |
|---|---|---|
| 有可用观察，且无降级/缺失 | `succeeded` | 完整结果 |
| 有可用观察，但部分 Agent 降级或资料缺失 | `partial` | 保留有效证据及疑点 |
| 无可用观察或内部 `insufficient_data` | `needs_input` | 给出 `missing_data`，不编造结论 |
| 内部 `failed/cancelled` 或适配异常 | `/fail` | 后端记录稳定错误码；不会回调伪成功 |

### 证据边界

证据键为 `(source_type, source_id, source_version, locator)`，必须与冻结快照完全一致。一个观察引用了快照外记录时，整个观察会从回调中排除。证据不会引用未解决医学冲突。当前后端的患者查询结果还带 `source_deleted` 等业务侧派生信息，该字段由后端负责，不在 Agent 回调中发送。

## 5. 部署配置与操作

需要 Python 3.12+。启动 Agent 服务前设置：

```powershell
$env:GCA_MODE = "mock"                      # 联调；真实模型改为 live 并配置模型 Key
$env:GCA_INTERNAL_TOKEN = "<agent-service-token>"
$env:GCA_BACKEND_BASE_URL = "https://<backend-internal-host>"
$env:GCA_BACKEND_SERVICE_TOKEN = "<backend-service-token>"
python -m gutcare_agents serve
```

后端 Worker 已部署时由它派发。仅在开发环境缺少 Worker 时，另一个终端使用同一组环境变量执行 `python tools/f08_claim_once.py --agent-url http://127.0.0.1:8100`。脚本先检查 Agent 存活，再领取一条任务并派发；输出不含令牌或患者数据。若还设置了 `GCA_PATIENT_TOKEN`，可加 `--wait-seconds 60`，由患者身份轮询最终状态。真实后端患者查询不能用服务令牌代替。

`GCA_MODE=live` 需要 `GCA_API_KEY`、`GCA_BASE_URL`、模型名称等配置；`mock` 的成功只说明协议链正常，不说明模型推理质量。生产环境还须使用 HTTPS、独立服务凭据和持久化任务队列/重试机制。

## 9. F09 建议格式转换（已实现，2026-10-19）

`gutcare_agents/f09_adapter.py` 的 `map_f09_advice` 将 F08 内部报告中**已通过建议校验的条目**转成后端 `AdviceCallback` 的 `callback_id/schema_version/advice[]`。调用方必须传入后端已接受的 F08 状态（仅 `succeeded/partial`）；转换器重新校验冻结输入和患者身份，再按观察 ID 找回快照内的患者记录证据，输出精确的来源类型、ID、版本和 locator。类别映射为 F09 枚举：`activity→lifestyle`、`medication→medication_adherence`、`seek_care→care_consultation`，其余已有对应项保持不变。适用范围保守地设为 `general`，不从自由文本推断“疾病专属”；不确定性设为 `high`，保留原有说明；安全边界固定声明“不诊断、不处方、风险优先”。

知识证据只接受调用方明确传入、标记 `approved` 且带版本、标题和发布方的元数据。当前 6 条 `unverified_demo` 条目**不会自动成为 F09 知识证据**。任何建议若引用了未确认观察、快照外记录或未审核/元数据不完整的知识条目，整条建议被跳过，原因记录在 `F09Mapping.dropped`；返回 `ready=false` 时不得发送空建议回调。转换器不改写患者事实，不调用后端，也不宣称医学审核已完成。

`tests/test_f09_adapter.py` 覆盖患者证据精确映射、未确认或越界证据整条拒绝、演示知识拒绝、已审核知识格式与不合格 F08 状态。设置 `GCA_BACKEND_SOURCE=<后端仓库目录>` 后，测试还直接使用最新后端 `AdviceCallbackBody` 模型验证输出结构；2026-10-19 对提交 `ac45fa0d` 的该项模型校验通过。下一步是调用独立 F09 callback、保存回调内容供幂等重发，并在真实后端复核任务状态和授权竞态。
