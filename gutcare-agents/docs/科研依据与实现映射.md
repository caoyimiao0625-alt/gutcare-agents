# GutCare 科研依据与现有实现映射

更新时间：2026-10-18。本文用于技术方案、项目说明和答辩准备。所列论文均有公开可读的原文页面；引用它们表示**设计依据或后续评测方法**，不表示本项目复现了论文系统、取得了论文指标，或完成了临床验证。代码状态以本仓库当前实现为准。

## 1. 系统中真正自主实现的部分

GutCare 使用第三方模型处理图像理解和语言生成，但智能体系统并非一次模型 API 调用。项目自身实现了：

1. `orchestrator.py` 的阶段化任务编排：按输入条件调用领域智能体，再执行趋势、建议和校验；领域任务可并行运行，失败有明确降级语义。
2. `stats.py` 的确定性跨记录统计，包括时间窗、记录充足性和心情数据统计；这部分不由模型自由编造。
3. `knowledge_base.py` 的本地字符二元组与 TF-IDF 检索，以及 `advice.py` 的检索后生成和知识条目引用。
4. `validation.py` 的结构、来源引用、数值与安全表述校验；`f08_adapter.py` 将证据严格映射到后端冻结快照，并处理派发、回调和重试。
5. `eval/run_eval.py` 的有限本地评测，包括来源记录 ID 的精确率/召回率和安全规则阳性召回。

这些是**系统工程与应用方法**，不是自研基础模型。当前 `mock` 闭环只能证明流程和契约；真实识图、医学知识质量及医疗效果仍需单独验证。

|---|---|---|---|
| 多智能体协作：[Wu 等，*AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation*，2023](https://arxiv.org/abs/2308.08155) | **架构参考**：论文研究可定制智能体的协作与工具使用。GutCare 采用专职智能体和固定阶段编排。 | `orchestrator.py`、`agents/`；Medical/Diet/Stool、Trend、Advice、Conversation 各有独立职责。 | 没有使用 AutoGen 框架，也没有实现论文中的自由对话式协作；不能写“基于 AutoGen 实现”。 |
| 检索辅助生成：[Lewis 等，*Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*，NeurIPS 2020](https://arxiv.org/abs/2005.11401) | **方法借鉴**：生成前检索外部资料，减少完全依赖模型参数知识。 | `knowledge_base.py` 以字符二元组 + TF-IDF 搜索本地条目；`advice.py` 检索前 3 条并要求引用。 | 没有复现论文的密集向量检索、维基百科索引、联合训练或论文实验指标；当前 6 个知识条目均为 `unverified_demo`。 |
| 可归因生成：[Rashkin 等，*Measuring Attribution in Natural Language Generation Models*，Computational Linguistics 2023](https://aclanthology.org/2023.cl-4.2/) | **证据设计依据**：输出应能回指被识别的来源。 | `validation.py` 解析来源 ID；`f08_adapter.py` 仅接受与冻结快照完全匹配的来源类型、ID、版本和定位符。 | 现有校验不逐句判断语义是否被证据支持，不能声称实现了论文的 AIS 评测或“零幻觉”。 |
| 原子事实核验：[Min 等，*FActScore: Fine-grained Atomic Evaluation of Factual Precision in Long Form Text Generation*，EMNLP 2023](https://arxiv.org/abs/2305.14251) | **后续评测参考**：可将报告拆成独立事实，再测每条事实的证据支持情况。 | 当前已有结构化 `observations` 和来源引用，具备构建该评测集的基础。 | 尚未运行 FActScore，也没有其事实精度分数。 |
| 多维模型评测：[Liang 等，*Holistic Evaluation of Language Models*，2022/2023](https://arxiv.org/abs/2211.09110) | **评测框架参考**：除正确率外，还应考察稳健性、效率和风险。 | `eval/run_eval.py` 有来源 ID 精确率/召回率、安全规则召回；已有本地契约测试。 | 没有运行 HELM，也不能把流程测试写成模型准确率或临床安全性证明。 |
| 医疗领域 RAG 基准：[Xiong 等，*Benchmarking Retrieval-Augmented Generation for Medicine*，2024](https://arxiv.org/abs/2402.13178) | **领域局限与未来对标**：医疗问答需要专门语料、基准和检索评测。 | 当前 Advice 已有可替换的知识检索接口；可据此设计人工审核后的医学问答与证据集。 | 尚未使用 MedRAG/MIRAGE 基准，演示知识库不能视为合格医学知识库；不能沿用论文的效果结论。 |

论文结果适用于各自的模型、数据和实验条件，不能直接推断 GutCare 的准确率。这里的“已落地”只表示代码存在并有相应本地验证，不代表所有模块已在真实后端或真实模型下验收。

## 3. 可用于技术方案或答辩的准确表述

> GutCare 采用领域分工和阶段化编排，将报告、饮食、排便等输入处理与跨记录趋势分析、知识辅助建议和输出校验拆成可组合任务。系统使用第三方模型进行视觉理解及语言生成，同时自行实现确定性统计、本地知识检索、来源校验、后端冻结证据映射与任务回调。多智能体协作、检索辅助生成和可归因生成的相关研究为设计提供了参考；本项目没有复现 AutoGen 或原版 RAG 算法。当前完成了本地协议闭环，真实模型准确率、知识库医学审核和真实业务后端联调仍是后续验收项。

如果需要突出“创新点”，宜写**面向肠道健康记录的任务拆分、已确认数据与候选识别分离、冻结快照证据追踪、缺失/冲突数据降级和可恢复任务回调**。这些是项目自身可以展示代码和测试的集成创新；不应宣称基础模型、论文算法或临床疗效创新。

## 4. 下一步让论文依据转为可检验结果

1. 用经审核、带版本和出处的知识条目替换 `unverified_demo` 条目；记录审核者、日期、适用范围与更新机制。
2. 建立带人工标注的测试集：报告字段、菜品识别、排便候选分类、趋势事实、知识引用与危险征象分别评测；把 `mock`、`live` 和人工标注结果分开报告。
3. 对最终报告逐条人工标注“证据支持 / 部分支持 / 无支持”，再计算事实支持率；该指标属于本项目评测，只有实际实现并运行后才可引用。
4. 增加无检索、无校验、单阶段模型调用等消融对照，在同一测试集上比较证据支持率、安全输出、延迟与成本；当前 `eval/ablation.py` 可作起点，但不能预填结论。
5. 在真实业务后端运行 F08 任务，并记录“领取—分析—回调—患者查询”的可复现实测日志；本地模拟后端测试与真实后端验收须分开陈述。
