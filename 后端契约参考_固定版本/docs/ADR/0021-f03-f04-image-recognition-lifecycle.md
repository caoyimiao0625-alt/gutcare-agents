# ADR-0021：F03/F04 记录图片与专用识别任务

- 状态：已采纳（设计冻结；未实现）
- 日期：2026-10-18
- 范围：F03 饮食记录图片及识别、F04 排便记录图片及识别的业务数据模型、API、Agent 内部传输、授权、候选确认和生命周期。不包含运行时代码、Alembic 文件、模型推理和临床规则。

## 背景

现有饮食/排便 CRUD 只允许 `image_object_id` 单图字段；F03 功能定义要求可多图，且图像识别尚未有独立任务、候选持久化和患者确认闭环。复用 F08 会把单记录识别错误并入综合分析快照与状态机。复用 F02 `medical_document` 也会将健康记录图片错误分类为医疗档案。

## 决策

1. **复用既有文件链路，不新增 medical_document。** 图片通过 `health.upload_session`、`health.file_object`、同源 HTTPS gateway 上传/下载，purpose 使用既有 `diet_image`/`stool_image`；上传申请与附件关联要求当前 `health_data_processing` 和 `sensitive_image`，完成校验、ClamAV clean 后才可关联。APP 不接触 MinIO、bucket/key、永久 URL 或存储凭据。F02 `medical_document` 仅用于报告档案。
2. **图片归属采用分表和严格复合外键。** 新增 `health.diet_record_image`、`health.stool_record_image`，均含 `id, patient_id, record_id, file_object_id, position, created_at, deleted_at`；对记录使用 `(record_id, patient_id)` 复合 FK，对文件使用 `(file_object_id, patient_id)` 复合 FK。记录表须有相应 `(id, patient_id)` 唯一键。每个 file object 只能有一个记录附件归属；记录删除/附件删除同步使附件不可用并进入既有七天文件删除队列。Diet `position CHECK 0–9` 加上患者/记录内有效位置部分唯一索引，数据库可强制最多10张；position 连续性由事务服务维护。Stool `position CHECK=0` 加上 `UNIQUE(record_id, patient_id) WHERE deleted_at IS NULL` 部分唯一索引强制每条记录最多1张，删除后可添加替代图片。旧 `image_object_id` 请求字段移除；附件资源成为唯一关系来源。
3. **手工记录与识别互不依赖。** 饮食/排便记录 CRUD 可先保存无图记录；上传或识别失败不阻断手工 CRUD。用户先创建记录，再将图片关联到该记录。附件添加/移除是独立版本化操作，不隐式 PATCH 记录字段。附件集合变更递增父记录 `record_version`，同时递增 `image_set_version`。识别请求保存原始 `record_version`/`image_set_version` 和可变 `decision_record_version`（初值等于原 record_version）；同一识别请求内逐候选确认时，患者决定接口必须提交当前 record_version，成功后同步递增记录版本和 `decision_record_version`，允许继续决定其余候选。若发生任何非本 request 的记录编辑，或图集版本变化，则 request 失效并使剩余候选 invalidated。每条记录同一时刻最多有一个非终态识别请求；重复创建请求通过患者+record+`Idempotency-Key` 幂等，相同摘要返回同一 request，不同摘要 409。
4. **识别是独立于 F08/F02 的专用任务。** 新增 `analysis.record_image_recognition_request`、canonical 关系快照 `analysis.record_image_request_attachment` 与 `analysis.record_image_candidate`，支持 `diet_image_recognition` 和 `stool_image_recognition`。业务 Worker 是唯一 claim 者，使用行锁 `SKIP LOCKED` 和五分钟 lease；Agent 不 claim、不访问数据库。任务绑定单个 record、患者、record_version、image_set_version、附件 ID/文件版本及 request schema version。附件快照不使用 JSONB；按 diet/stool 两个 nullable 类型化 attachment ID 存于关系表，用 XOR、患者复合外键及约束触发器保证附件类型与 request 一致；`(request_id,position)` 为主键，`uq_record_image_request_attachment_diet_per_request` / `uq_record_image_request_attachment_stool_per_request` 保证仅同一 request 内同类型附件唯一，但不同 request/显式 retry 可以复用同一来源附件，并分别冻结各自 `file_version`。图片输入仅可经任务级短时只读能力读取，能力在每次读取重新校验患者归属、文件 available、request 非终态、授权仍有效和文件仍在冻结附件集；读取完成即关闭能力，不签发可复用或患者级 URL。识别服务不可用或超时时，任务进入 `failed`（受限 `reason_code`），记录和附件仍可正常查看、修改、删除。
5. **授权与告知。** 创建、claim、每次图片读取、成功/失败回调、患者逐项确认均须同时具备当前有效 `health_data_processing`、`sensitive_image`、`third_party_ai`，并取得本次请求的 purpose-specific disclosure acknowledgment。告知制品新增 `diet_image_recognition`、`stool_image_recognition` 用途条目，分别有独立 policy version 与摘要哈希配置（不与 consent 哈希混用），明确图片类别、字段、处理者、短时处理与删除期；`GET /record-image-recognition-disclosures?purpose=...` 返回当前正文，客户端确认后 `POST /record-image-recognition-disclosures` 取得绑定患者/记录/用途/记录版本/图集版本/告知版本的一次性、五分钟有效 disclosure token。创建 request 需提交 token 和完全匹配的版本，数据库只存 token hash、上述绑定及确认时间，不把客户端布尔值当证据。缺 consent 返回 409 `CONSENT_REQUIRED`；告知配置不可用或 production 仍为 test-only 时 fail closed，不创建任务。只允许读取/删除本人已有记录的权利不被撤回锁死；撤回任一所需授权时，同一患者 advisory consent fence 内取消该患者所有非终态对应识别请求，关闭能力、清除未确认候选的 value/locator，并拒绝迟到结果与确认。
6. **结果只作候选，逐字段确认并显式分组。** Agent 对每张图返回质量 (`usable|unusable|uncertain`)、受控 `reason_code`、置信等级 (`low|medium|high`) 与候选项。饮食候选类型仅为 `food_name|food_category|portion_description`；`food_category` 必须是现有受控 category code（`grain_staple/vegetable/fruit/meat/seafood/dairy/egg/legume/snack/beverage/mixed_dish/other`），名称和粗略份量为≤160字文本，`portion_description` 确认后映射到 `DietItem.amount_text`。不再输出或保存 `cooking_method` 候选。每个饮食候选必须带随机 UUID `candidate_group_key`，该 opaque key 仅在单个 request 内标识一个候选食物项；同 request 可在不同附件上显式复用该 key 表示同一项，且 `(request_id, candidate_group_key, candidate_type)` 唯一。Agent/业务端禁止根据文本、类别、图片坐标或附件相似度推断分组，禁止跨 request 合并；重试新 request 必须使用新 group key。排便候选只允许 `bristol_type`，不带 group key，也不输出 `visible_morphology/visual_tag`。每个 candidate 另有稳定 ID、候选版本、图片附件来源 ID、受控 locator（图中归一化区域；可空）及不确定性。

   候选永不作为事实。饮食 `diet_item.name` 保持 NOT NULL，不建立 partial/draft item。只有 `food_name` 的 accept/edit 能创建该组 `diet_item`；同一事务写入患者确认名称、分配稳定 `item_position`、设置 `source_recognition_request_id` 与 `source_candidate_group_key`，并逐项记录决定。Manual diet item 的两个来源字段均为 NULL。只有该组名称已被 accept/edit 并创建 item 后，`food_category` 和 `portion_description` 才能分别 accept/edit 并写入 `category_code` 和 `amount_text`；否则以 HTTP 409 `candidate_dependency_unmet` 无副作用拒绝该决定，候选仍 pending。edit 写入患者编辑后的值，绝不写入未确认 Agent 值。`food_name` 被 reject 时不建 item，并在同一事务把该组其他 pending category/portion 候选设为 `invalidated`、清除其 value/locator；拒绝其他字段只影响该字段。每字段仍需独立显式决定。

   同 request 同 group 同 type 只允许一个候选；多个组、多个附件或多个 request 不因值相同而自动合并。`item_position` 在名称首次确认并创建 item 的事务中分配，创建后不因重试、重复决定、编辑、附件顺序或 callback 顺序重新编号。只有有效的名称确认会产生饮食项；类别/份量确认仅更新同组已存在项。各决定、事实写入、record version 推进、不可变 decision history、幂等收据在同一事务完成；相同 Idempotency-Key/摘要回放原响应且不重复写事实/版本/历史，异摘要 409。dependency 409 不消费候选且不改事实，之后须由患者在名称已确认后发起新明确操作并使用新 key。旧版本、非 pending 候选、迟到 callback、已 invalidated group 均拒绝。任何手动编辑都遵循现有版本规则并使相关未决候选失效；重试创建新 request/new group，不能覆盖或合并已确认项。

   候选不进入 `diet_item`/`stool_record`、详情事实视图、导出、趋势、F10 风险、F08 快照或建议；只有患者已确认/编辑字段进入对应事实字段。决定后 candidate value 和 locator 当事务清除；已确认值仅保留在患者事实表，decision ledger 只保留候选 ID、动作、类型、时间和 request ref。`record_version` 或 `image_set_version` 变化即让待确认候选失效；已作决定不回滚。
7. **严格输出边界。** 不生成精确卡路里、宏/微量营养素、过敏原、隐藏食材或因果结论；不判断/推断出血、疾病、诊断、严重性或风险，不触发/改变风险规则。排便颜色仅可保留图像可见的中性描述标签，不能映射为血液或疾病。模型分数不映射为风险或临床概率。禁止持久化 prompt、原始模型输出、报告正文、完整图片 URL/capability、图片派生人脸/身份信息；只存通过白名单校验的规范化候选和受控错误码。
8. **状态、锁、幂等与回调。** request 状态 `pending → processing → candidates_ready | no_candidates | failed | cancelled | invalidated`；终态不接受迟到回调。候选状态 `pending → accepted|edited|rejected|invalidated`。业务 Worker 独占 claim，lease 到期可恢复；内部回调以 callback UUID + payload hash 去重，重复同摘要 204、异摘要 409。患者通过 `POST /record-image-recognition-requests/{request_id}/retry` 显式重试；仅父状态 `failed/cancelled/invalidated` 且来源记录/附件仍存在时允许。重试请求使用 `Idempotency-Key`、当前 `record_version/image_set_version` 和重新确认后签发的新 purpose disclosure token；服务端重验三授权、用途告知、来源版本与当前附件集合，在统一事务创建新 request、新 FK 附件快照和新 attempt（`retry_of_request_id=parent.id`、`attempt=parent.attempt+1`）。同键同摘要回放新 request，异摘要 409；parent 仅允许一个直接 retry child，阻止不同幂等键制造同 attempt 分支。父 request 不变；capability、候选、group key 均不复用。父非终态/源版本不匹配/已有活动 request 返回 409，跨患者 parent 返回 404。创建、claim、input read、callback、decision、retry、附件/源记录删除、授权撤回共用 F02/ADR-0011 患者 consent fence 与统一锁顺序：advisory fence → record → request → candidates → attachments。候选决定同时校验 `candidate_version`、当前 `record_version` 等于 request `decision_record_version`、当前 `image_set_version` 等于冻结值。Diet callback 对 group key 做 request 内 UUID 校验，并按 `(request_id, candidate_group_key, candidate_type)` 去重；group 的跨附件复用只接受 Agent 显式提供。food_name accept/edit 的 item 创建与 `item_position` 分配、事实字段变更、候选状态/value 脱敏、decision history、幂等收据及 record_version 推进原子提交；category/portion 决定先验证同组已存在的 confirmed diet_item，否则 409 `candidate_dependency_unmet` 且无部分写。name reject 原子 invalidates/清除同组未决 category/portion。Stool Bristol 决定只更新患者已确认 Bristol 字段，无分组/形态副作用。重复幂等回放不再递增；外部 record PATCH/DELETE 或 attachment 变化先失效请求/未决候选，再继续写入。迟到/重复组类型/未知候选字段均按契约拒绝。失败不自动创建 retry。
9. **RLS 与角色。** 两张附件表和患者可见确认/幂等表启用并强制 RLS；所有患者外键复合含 patient_id。Agent 无 DB 角色。`gutcare_app` 可按患者 RLS 管理记录附件、读取任务和候选并决定；业务 analysis worker 仅可 claim/lease、建立任务能力和提交受限回调；Agent 只持服务间 Bearer，调用任务 ID 级输入与回调；privacy/file worker 按职责清理对象和墓碑，不持有候选确认权。检查约束要求 diet position≥0、stool 最多一条、request record 与患者复合归属匹配、快照引用的附件属同患者且 file purpose 匹配。
10. **删除、保留、导出与撤回。** 删除单图即刻撤销读取能力、从详情/候选来源隐藏并使绑定 request 失效，文件进入既有七天物理删除队列；记录附件关系行在对象删除与 F03 子记录清理事务内先删除，之后才可物理删除 `file_object` 元数据，避免违反复合 FK。删除饮食/排便记录时同事务撤销全部关联能力、取消任务、清除未确认候选内容与 locator，并标记已确认识别来源 `basis_updated`/`source_deleted`，保留用户已确认记录值。候选决定后即时清除候选 value/locator，accepted/edited 值仅保留在患者事实表，decision ledger 保留受限动作元数据。记录和确认决定作为该记录数据在 F13 导出中按 `diet`/`stool` 类别包含；当前图片可用且用户选择对应类别时，以现有加密 ZIP 和一次性 gateway 能力导出，不单独新增 category。注销 inventory 覆盖附件、请求、候选、决定和对象；按 F13 对象字节与业务数据阶段协调处理 F03 外键关系，最长 30 天。留存期限沿用记录 7 天、对象 7 天、备份最多 35 天、去标识安全审计 180 天；审计不含图像、候选值、对象 key、完整 locator、token 或模型输出。
11. **每次 UI 明示。** 图片选择前呈现与当次用途匹配的隐私告知和第三方处理披露；每次识别请求显式二次确认“将本次所选饮食/排便图片交由已披露的智能服务生成待确认候选”，拒绝或服务不可用均返回原记录编辑流程。不得将上传本身视为识别同意，不得后台静默自动提交 Agent。

## API 契约

患者端新增：`POST /dietary-records/{record_id}/images` 与 `POST /stool-records/{record_id}/images` 关联已完成 F02 file object；GET 对应 `/images` 列表；DELETE `/{image_id}` 版本化删除。`GET /record-image-recognition-disclosures?purpose=...` 返回当前目的告知，`POST /record-image-recognition-disclosures` 记录当次确认并返回一次性 token；需传当前 record/image-set version 且 token 五分钟内只能消费一次。`POST /dietary-records/{record_id}/image-recognition-requests`、`POST /stool-records/{record_id}/image-recognition-requests` 需 `Idempotency-Key`、当前 `record_version`、`image_set_version`、disclosure token；`GET /record-image-recognition-requests/{request_id}` 查询状态/候选。显式重试使用 `POST /record-image-recognition-requests/{request_id}/retry` + `Idempotency-Key`，body 复用创建 DTO（当前 record/image-set version 与新鲜 token），返回 202 新 request。仅 failed/cancelled/invalidated 且源仍存在可重试；版本/活动任务冲突 409，跨患者 404；新 request 指向 parent 并使用新 attempt、快照、能力和候选。`POST /record-image-candidates/{candidate_id}/decision` 需当前候选版本、当前 record/image-set version、`accept|edit|reject`、编辑值（仅 edit）和 Idempotency-Key，返回 204。Diet `food_category/portion_description` 在该组 `food_name` 已确认创建 item 前决定时返回 RFC 9457 409 `candidate_dependency_unmet`；无其他副作用，名称拒绝时同组其他待决候选失效并脱敏。图片关联只接受对应用途且 clean/available、同患者文件；stool 第 2 张返回 409 `ATTACHMENT_LIMIT_REACHED`。所有错误为 RFC 9457。

智能体内部契约（路径根 `/internal/v1`）：业务 Worker 派发 `POST /internal/v1/record-image-recognition/requests`；业务端托管 `GET /internal/v1/agent/record-image-recognition/requests/{request_id}/input`、`GET /internal/v1/agent/record-image-recognition/images/{capability}`、`POST /internal/v1/agent/record-image-recognition/requests/{request_id}/candidates` 与 `POST /internal/v1/agent/record-image-recognition/requests/{request_id}/fail`，业务 Worker 通过 `POST /internal/v1/agent/record-image-recognition/claim` 原子领取任务。Input 仅返回任务标识/类型、冻结 record/image-set 版本、严格结构化的非敏感必要记录字段、附件元数据和仅当前请求/当前图片一次读取的短时 opaque image capability；不得包含患者身份/跨任务查询入口。回调必须原样绑定 request ID、attachment ID、record/image-set version 和 schema version。OpenAPI 与 Agent YAML 例子只使用合成 UUID/图片能力。

## 后果与验收

需新增 Alembic 增量迁移和数据库角色授权（本 ADR 不生成迁移文件）；同步 OpenAPI、Agent 契约、F03/F04、数据库设计、数据字典、隐私生命周期、开发边界、导航、联调/实施计划、测试与追踪矩阵。T133–T140 还覆盖类型化附件快照复合 FK/XOR/type trigger、显式重试状态/来源/授权/version/idempotency/attempt/new snapshot 与 Agent dispatch metadata；candidate_group_key 的同组/跨附件/不跨 request 语义、diet 仅三类候选及 category 受控值、先 category 返回 dependency 409、name 后逐项成功、name reject 使同组待决字段失效、多个组不自动合并、稳定 item_position、并发/重复幂等/version/迟到 callback/手工编辑/retry 不覆盖事实，以及 GET/export/F08/F11 只读取患者确认值。契约状态为 `specified`；不得报告已实现或已验证。

外部阻断：production purpose-specific 告知的法律/隐私签核、第三方 AI 处理者合同与留存确认、Agent 团队识别 schema/错误码/超时 SLA 与模型安全评测、双端 APP 图片选择与安全区真机证据、真实 PostgreSQL 18/MinIO/ClamAV 集成及 F13 恢复演练均待后续阶段完成。未经临床专业审核的候选范围不涉及诊断与风险规则；生产发布需先经产品/隐私/临床安全审阅。
